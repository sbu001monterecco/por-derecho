# Thread deletion and evidence-custody closeout prompt

**Date:** 21 August 2026  
**Purpose:** make a ChatGPT thread safe to delete without overstating evidence
custody or placing restricted material in public GitHub.

## Operating instruction

Assume the current conversation will be deleted. Perform a complete,
document-led closeout of the thread and the current repository. Do not rely on
the chat remaining available.

### 1. Establish the controlling baseline

1. Read `CHATGPT_START_HERE.md`, the current handover, the evidence-custody
   protocol, correction register, missing-evidence register and current `main`.
2. Identify the last merged repository commit and any unmerged local, branch or
   pull-request work.
3. Separate material created in this thread from material merely discussed or
   linked to it.
4. Do not change public claims merely to complete a deletion audit.

### 2. Inventory the complete thread

Record every material:

- source, attachment and source-system locator;
- factual proposition, correction and contradiction;
- first-hand account, interpretation and legal argument;
- entity, individual, right-holder and claimed loss;
- proceeding, deadline, live action and missing-document request;
- repository or website edit, draft, prompt and strategic decision; and
- private identifier, email address, privileged item or restricted document.

Maintain the categories `VERIFIED FACT`, `EVIDENCE-BASED INFERENCE`, `GROUP
POSITION`, `FIRST-HAND ACCOUNT`, `LEGAL ARGUMENT`, `OPEN QUESTION` and
`CONTRARY/EXCULPATORY MATERIAL`.

### 3. Apply the bytes-plus-hash custody test

For every file, record:

`exact supplied filename | source system | date | size | SHA-256 | status |
custodian | repository record | private retrieval locator | next finite step`.

Use only these custody statuses:

- `ORIGINAL VERIFIED`: the supplied bytes are available and fingerprinted;
- `BYTE-IDENTICAL COPY`: both items are available and their hashes match;
- `EXACT-NAME RECOVERED CANDIDATE`: a source-system file has the same name, but
  the supplied bytes are unavailable for hash comparison;
- `DERIVATIVE`: a print, export, scan, OCR or other transformed copy;
- `RELATED SOURCE`: a source document related to the supplied file but not a
  proven replacement;
- `VARIANT`: a compressed, renamed, redacted or otherwise different version;
- `MISSING-EXACT`: no exact supplied-byte copy has been recovered; and
- `REFERENCE ONLY`: the file is identified but no native bytes are held.

Never say a file is stored, preserved, original or identical unless the bytes
exist in the stated system and the claim is supported by a computed hash or an
equally specific custody record. Filename identity alone is not byte identity.

### 4. Separate repository continuity from evidence custody

The public repository may hold:

- public-safe analytical controls, prompts, manifests and source codes;
- filenames where publication itself is safe;
- hashes, sizes and non-sensitive provenance descriptions; and
- finite retrieval steps and links to canonical public records.

The public repository must not receive private email addresses, raw private
message IDs, signed download URLs, credentials, privileged advice, restricted
personal data or confidential evidence binaries merely to satisfy a deletion
audit. Keep those in the controlled source system or approved private evidence
vault. Record the existence and retrieval method in public-safe form.

Do not describe a temporary scratch-workspace copy as durable preservation.

### 6. Build the repository closeout

1. a unitary thread-deletion audit;

tests. Merge only when the record is accurate. Verify deployment only if public

### 7. Create an off-thread self-email record

Send a private closeout email to the authenticated account using `to: me`. The
email must state:

- repository, branch, pull request and merge commit when known;
- closeout verdict;
- each attachment's custody status, size and SHA-256 where computed;
- private source-system retrieval locators;
- unresolved exact originals and their finite retrieval steps;
- which binaries were deliberately excluded from public GitHub and why; and
- any connector failure that prevented a native-message or attachment copy.

Do not say the evidence was attached if only a manifest or source locator was
sent. Verify that the email action returned a sent-message identifier.

### 8. Required final answer

Choose exactly one verdict:

- `DELETION-SAFE`: all material thread intelligence and required custody copies
  are durably preserved;
- `DELETION-SAFE WITH OPEN CUSTODY`: analytical continuity is preserved, but one
  or more exact native files still need retrieval or independent custody; or
- `NOT SAFE TO DELETE`: material thread intelligence or irreplaceable source
  material remains only in the conversation.

Report the merged pull request, merge commit, validation performed, self-email
subject, sent status, attachment results and every open custody item. Distinguish
what is complete from what remains recoverable.
