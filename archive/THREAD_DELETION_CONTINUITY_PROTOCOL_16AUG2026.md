# UNIVERSAL THREAD-DELETION CONTINUITY PROTOCOL

**Date:** 16 August 2026  
**Status:** controlling repository-wide continuity rule for Project Sun Rock / Por Derecho ChatGPT work.  
**Action-state companion added:** 25 August 2026.

## Purpose

No Project Sun Rock / Por Derecho ChatGPT conversation should become a single point of institutional memory.

This protocol applies to **every Project Sun Rock / Por Derecho chat or thread**, regardless of topic or length. A thread that creates no material project intelligence may receive a brief `DELETION-SAFE — no material project intelligence created` close-out, but it must still be assessed rather than silently exempted.

The rule therefore covers, without limitation:

- Ministerio Fiscal / Fiscalía;
- courts, judges, LAJs, Administrador Concursal and appellate proceedings;
- Acosta Matos / CAM / HNT / MYND / Canarian Hospitality;
- RICPE / RIC / CNMV / AGM / Orion / Portfolio;
- banking, creditor, PH122, SAREB, enforcement and insolvency-origin work;
- AEAT, ATC, Yaiza, Cabildo, Gobierno de Canarias, Intervención, SNCA/IGAE/FEDER;
- professional-regulator tracks;
- media-accountability tracks;
- website, navigation, public communications and institutional marks;
- books, manuscripts and research architecture;
- investor, recovery, restitution and damages work;
- any new track created in a future conversation.

Topic-specific deletion audits or handovers may supplement this protocol, but they do **not** replace it.

## Universal continuity gate

Before any project thread is treated as deletion-safe, ask:

> **If this entire conversation disappeared now, could a fresh ChatGPT recover every material new fact, source-status decision, correction, strategic choice, open question, retrieval target and implementation state from current `main` plus the connected primary-source systems?**

If the answer is not clearly yes, the thread is **NOT deletion-safe**.

For a thread that created no material project intelligence, the answer may be recorded briefly, but the gate still applies.

## Controlling action-state companion

Every deletion audit and future-thread handoff must apply:

- `.github/governance/CHATGPT_ACTION_STATE_AND_THREAD_CLOSEOUT_GOVERNANCE_25AUG2026.md`; and
- `.github/governance/CHATGPT_ACTION_STATE_AND_THREAD_CLOSEOUT_GOVERNANCE_25AUG2026.json`.

The companion governs the distinction between `DISCOVERED`, `ANALYSED`, `PROPOSED`, `PREPARED`, `AUTHORIZED`, `EXECUTED`, `VERIFIED`, `HOLD`, `NO_ACTION_REQUIRED`, `BLOCKED`, `FAILED` and `SUPERSEDED`.

Do not collapse action states. In particular:

- branch/commit != PR open;
- PR open != merged;
- merged != deployed;
- deployed != independently edge-verified;
- email prepared != authorised != sent != verified;
- institutional receipt != docketing != procedural action != substantive decision;
- existing page strengthened != new page created; and
- deliberate hold != failure.

A broad instruction such as “I follow your judgment” or “do it now” implements the latest clearly stated recommended course within the authorised scope. It does not reverse a `HOLD` recommendation, bypass an email/final-package hard stop or extend repository authority to another external channel.

## What must be captured

For every thread that created or changed project intelligence, identify whether it created or materially changed any of the following:

1. verified facts or primary-source findings;
2. party allegations or evidence-based inferences;
3. contradictions, corrections or superseded propositions;
4. proceeding status, dates, parties, competence or routing;
5. actor/entity relationships or legal-person distinctions;
6. source provenance, evidential classification or limitations;
7. missing-evidence requests, retrieval routes or source-completion priorities;
8. strategic objectives, remedies, recovery theories or counterfactual questions;
9. public-writing or publication safeguards;
10. website/page architecture, links, bilingual parity or institutional-mark decisions;
11. public/private/privileged/restricted treatment decisions;
12. branch, PR, merge or deployment state;
13. unfinished work that a future thread must continue;
14. any user instruction that materially changes how future Project Sun Rock / Por Derecho work must be performed;
15. the exact state of each material external action, including what was deliberately not done; and
16. the trigger required to move from `HOLD`, `NO_ACTION_REQUIRED` or `BLOCKED` to a later action.

Every material item must be either:

- incorporated into the appropriate canonical repository record; or
- explicitly recorded as an open item, excluded item or unresolved question with the reason it was not incorporated.

## Canonical destinations

Use existing canonical records rather than creating competing summaries wherever possible:

- `CHATGPT_START_HERE.md` — controlling bootstrap and universal operating rules;
- `archive/CONTINUOUS_MAINTENANCE_MATRIX.md` — current track state and next actions;
- `archive/MISSING_EVIDENCE_REGISTER.md` — one canonical source-completion queue;
- `archive/CORRECTION_REGISTER.md` — permanent correction/supersession control;
- specialist ledgers/protocols for the affected track;
- `archive/DEPLOYMENT_LOG.md` — merged public-site deployment verification;
- `archive/CHATGPT_PROMPT_LIBRARY.md` — reusable operating prompts;
- this protocol — universal thread-deletion rule; and
- `.github/governance/CHATGPT_ACTION_STATE_AND_THREAD_CLOSEOUT_GOVERNANCE_25AUG2026.md` — exact action-state and completion-claim control.

Create a thread-specific handover/audit only when the conversation contains enough distinct material that a dedicated recovery map materially improves continuity. Do not create a proliferation of overlapping handovers for trivial or fully canonicalised work.

## Private-source boundary

Deletion-safety does **not** require copying private primary evidence into public GitHub.

Private, privileged, personal, restricted, tax, evidential or redistribution-sensitive material should remain in its proper source system. The repository should preserve enough public-safe metadata, evidence IDs, retrieval targets, source-status notes and analytical consequences for a fresh ChatGPT to know what must be re-queried.

When primary evidence is needed, a future thread must re-query connected Gmail, Google Drive, File Library/Files or another lawful primary source rather than reconstructing the evidence from conversational memory.

## Expired or unavailable chat files

An expired chat upload does not automatically make a thread unsafe where the material conclusion, evidence status, public-safe metadata, retrieval target and implementation state are already canonicalised and the exact bytes are not needed.

It does block any later task requiring those exact bytes, exact attachment comparison, hashing, forensic review or verbatim source analysis until the file is re-uploaded or lawfully re-materialised from the source system.

Do not repeatedly request re-upload when the current task does not require the exact file. Do not infer from chat expiry that the original source is nonexistent.

## Evidence discipline during continuity capture

Deletion close-out must preserve the repository evidential categories:

- VERIFIED FACT;
- PARTY ALLEGATION;
- EVIDENCE-BASED INFERENCE;
- UNRESOLVED QUESTION;
- SUPERSEDED;
- CONTRADICTED/CORRECTED.

Do not strengthen a proposition merely because the conversation is ending. A deletion handover is not a vehicle for upgrading A1/H1 material into verified fact.

## Implementation state

A thread is not fully deletion-safe merely because its prose conclusions are remembered in an archive file. Where the thread made implementation changes, continuity must also preserve the state of those changes:

- intended files/pages;
- whether a canonical page already existed;
- whether the actual operation was review, strengthening, correction, new creation, route repair or no change;
- branch and PR where relevant;
- whether changes merged;
- exact merge commit where material;
- Pages/deployment verification for public-site changes;
- independent edge/read-back state where claimed;
- whether any communication was prepared, authorised, sent, verified, held or not required; and
- any failed, partial, superseded or deliberately deferred implementation.

A stale or unmerged PR must be recorded as such. Do not imply that an open branch is live or controlling. Do not report a page as created where an existing route was strengthened. Do not report a deliberate non-response as a failed send.

## Separate deletion-safety dimensions

Do not use one unqualified percentage or the word “complete” to cover materially different forms of readiness.

Assess separately, as applicable:

1. `THREAD_REASONING_CONTINUITY`;
2. `IMPLEMENTATION_STATE_CONTINUITY`;
3. `PRIMARY_EVIDENCE_COMPLETENESS`;
4. `LIVE_PUBLICATION_VERIFICATION`;
5. `COMMUNICATION_VERIFICATION`;
6. `CUSTODY_RESILIENCE`; and
7. `DISASTER_RECOVERY_SAFETY`.

A thread may be **DELETION-SAFE WITH OPEN EVIDENCE** where its reasoning, implementation state and retrieval targets are recoverable even though primary evidence, a current edge read-back, custody resilience or whole-repository disaster recovery remains qualified. State the qualification and do not silently convert it into a stronger claim.

## Email delivery rule for preservation/deletion threads

For any thread that performs a **backup, preservation export, disaster-recovery package, evidence-custody package, deletion-safety handover or other durable close-out artifact**, preserve a concise completion record outside the ChatGPT conversation. Connected Gmail capability does not authorise a send. Apply `EMAIL_SEND_FINAL_AUTHORIZATION_RULE.md`: no email, resend, forward or self-email may occur without the user's final approval of the exact recipient(s), body, attachments and links.

If the user gives that final email approval, the message should include or attach where practical:

- the final verified archive/package itself, subject to email size limits and confidentiality constraints;
- the verification/hash record or manifest;
- the preserved commit/version/date identifiers;
- the independent storage location(s); and
- the final deletion-safety status.

If the primary archive is too large or inappropriate to email, the approved message may identify precise retrieval/storage information instead. Email is an **additional delivery and notification channel**, not a substitute for repository canonicalisation, independent off-platform storage, hashing, custody controls or restoration testing.

Do not claim that an email was sent unless the Gmail send action actually succeeded. Repository publication, merge authority or an instruction using “and/or” does not imply email authority.

Where the latest institutional message is only a receipt or administrative acknowledgement and contains no express request or procedural opportunity, the default action is `NO RESPONSE REQUIRED / HOLD`. Do not reply merely to acknowledge an acknowledgement and do not send an updated website link as unsolicited evidence solely because the public page changed.

## End-of-thread checklist

Before declaring a project thread deletion-safe, verify as applicable:

1. current `main` was checked where the thread touched project state;
2. new material was classified;
3. canonical ledgers were updated or confirmed already sufficient;
4. corrections and contradictions were propagated;
5. missing evidence was added to the canonical queue where needed;
6. public/private boundaries were preserved;
7. any substantive repo change followed branch → review/diff → PR → merge;
8. public-site changes were deployment-verified and logged;
9. any claim of edge verification is supported by an actual current route/read-back check;
10. every material action has an exact state and proof;
11. what was deliberately not done is stated;
12. unfinished work and its trigger are recoverable without chat history;
13. a fresh ChatGPT can resume by reading `CHATGPT_START_HERE.md`, this protocol, the action-state companion and the named canonical files, then re-querying primary sources where required;
14. for backup/preservation/deletion-safety threads, the final verified package or completion record was preserved in an authorised durable destination; if the user separately approved an email, successful delivery was confirmed; and
15. thread continuity, primary-evidence completeness, live verification, custody and disaster-recovery claims have not been collapsed into one unsupported status.

If the thread genuinely created no material project intelligence and changed no project state, record that conclusion and no repository write is required solely to manufacture an audit artifact.

## Required close-out statement

For **every Project Sun Rock / Por Derecho conversation**, the continuity assessment should be one of:

- **DELETION-SAFE** — all material intelligence and implementation state are recoverable from controlled repository records and connected primary-source systems;
- **DELETION-SAFE — NO MATERIAL PROJECT INTELLIGENCE CREATED** — the thread produced nothing requiring canonical preservation;
- **DELETION-SAFE WITH OPEN EVIDENCE** — continuity is preserved, but identified primary evidence or another named verification dimension remains open; or
- **NOT DELETION-SAFE** — specified material remains conversation-dependent and must be canonicalised before deletion.

The close-out should identify any intentionally excluded private/privileged/restricted material and where a future thread must re-query it.
