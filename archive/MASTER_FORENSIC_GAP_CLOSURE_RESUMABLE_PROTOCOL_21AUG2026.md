# MASTER FORENSIC GAP-CLOSURE — RESUMABLE EXECUTION PROTOCOL

**Control date:** 21 August 2026  
**Matter:** Sun Park / MYND Yaiza / Aweswell–LPB–Matkator  
**Status:** canonical execution-control supplement for future ChatGPT/agent scans

## Purpose

This file preserves the execution architecture developed after repeated Gmail/attachment stalls during deep forensic scans. It does not replace the substantive Sun Park evidence modules. It governs **how** future exhaustive scans are executed so that one failed connector/attachment does not terminate the investigation or force a restart.

## Governing distinction

The Master Forensic Gap-Closure specification is the **governing forensic constitution**, not an instruction to consume Gmail, the File Library, legal research and final synthesis in one uninterrupted tool run.

The investigation must be:

- exhaustive in scope;
- small-batched in execution;
- resumable;
- checkpointed;
- evidence-led;
- non-restarting.

## Mandatory workflow

`DISCOVER → TRIAGE → RETRIEVE → READ → EXTRACT → CROSS-CHECK → UPDATE GAP → CHECKPOINT → STOP`

After each execution batch: **STOP**. Do not automatically move into the next forensic issue.

## One-batch rule

Each normal execution batch should contain:

1. one defined evidential question;
2. one principal repository;
3. one small family of materially related searches;
4. controlled retrieval;
5. primary-document reading;
6. fact extraction;
7. gap update;
8. checkpoint;
9. stop.

For Gmail, the preferred sequence is:

`SEARCH → REVIEW RESULTS → SELECT THREADS → INVENTORY ATTACHMENTS → PRIORITISE → RETRIEVE 1–3 P1 SOURCES → READ → EXTRACT → CHECKPOINT → STOP`.

Do not autonomously chain broad Gmail search → many attachment fetches → File Library search → legal research → synthesis → another Gmail search.

## Evidence acquisition ledger

Maintain a live ledger with, where available:

`SOURCE | REPOSITORY | QUERY | EMAIL/FILE | DATE | SENDER | RECIPIENT | SUBJECT | ATTACHMENT | FILE TYPE | RETRIEVAL STATUS | READ STATUS | GAP ADDRESSED | PROVENANCE | FOLLOW-UP`.

Permitted statuses:

- LOCATED
- RETRIEVED
- READ
- PARTIALLY READ
- DUPLICATE
- IRRELEVANT
- RETRIEVAL FAILED
- PARSING FAILED
- NOT ACCESSIBLE
- RETURN LATER

A filename or search snippet is not a read document.

## Attachment-failure rule

If a Gmail attachment, message read, Library file, parser or other tool call stalls/fails:

1. record the exact source/query/message/filename if identifiable;
2. mark `RETURN LATER`, `RETRIEVAL FAILED` or `PARSING FAILED`;
3. do not repeat the identical operation indefinitely;
4. preserve all findings already obtained;
5. continue only with another already-defined retrieval inside the same batch if safe;
6. do not broaden the investigation;
7. later search for duplicate, forwarded, renamed, Library, court or official copies;
8. expose the failure in the checkpoint.

**One failed attachment must never reset the wider programme.**

## No-restart rule

Never restart a completed search family merely because a later operation fails. Preserve:

- completed searches;
- documents located/read;
- source references;
- extracted dates/facts;
- contradictions;
- gap classifications;
- failed retrievals;
- outstanding P1 sources;
- next search vector.

“Fresh examination” means independent scrutiny, not needless repetition.

## Discovery before digestion

For attachment-heavy Gmail searches, first build:

`DATE | SENDER | RECIPIENT | SUBJECT | THREAD | ATTACHMENT | FILE TYPE | LIKELY RELEVANCE`.

Priority:

- **P1** potentially dispositive primary evidence;
- **P2** strong corroborative/gap-closing evidence;
- **P3** contextual evidence;
- **P4** duplicate/administrative/low-value material.

Read P1 before P2. Do not burn connector capacity on P4 while P1 gaps remain.

## Email / attachment separation

The email body and attachment are separate evidential objects. A readable email remains evidence even if its attachment fails. Likewise, a recovered attachment does not by itself prove who received it, when, or whether it was read.

## Duplicate control

Do not repeatedly parse identical attachments in long reply/forward chains. Preserve provenance/transmission where necessary, but prefer the earliest/native or most readable copy for substantive analysis.

## Checkpoint format

Every batch must end with:

- BATCH ID
- QUESTION
- REPOSITORY
- SEARCHES COMPLETED
- DOCUMENTS LOCATED
- DOCUMENTS ACTUALLY READ
- PRIMARY EVIDENCE FOUND
- NEW FACTS (A/B/C/D/E/F)
- GAPS CLOSED
- GAPS SUBSTANTIALLY CLOSED
- GAPS NARROWED
- GAPS OPEN
- CONTRADICTIONS
- FAILED/STALLED RETRIEVALS
- P1 SOURCES OUTSTANDING
- NEXT RECOMMENDED MICRO-BATCH
- **STOP**

## Internal search saturation

Do not stop after one failed query, but do not loop indefinitely. A material issue may reach internal search saturation once materially distinct searches have covered, where relevant:

- exact/variant names;
- entities/old names;
- email addresses;
- NIF/CIF;
- finca/CRU/cadastral references;
- procedure/NIG/IUP;
- key dates/amounts;
- filenames;
- Spanish/English terminology;
- known correspondents;

and materially new evidence has stopped emerging.

## Evidential classification

A. PRIMARY-DOCUMENT FACT  
B. INDEPENDENTLY CORROBORATED FACT  
C. PARTY ALLEGATION  
D. REASONED INFERENCE  
E. UNRESOLVED HYPOTHESIS  
F. DISPROVED / CONTRADICTED

Never silently upgrade C–E into A/B.

## Recovery after a stalled run

If a prior run visibly stalls on Gmail or an attachment, the next step is a checkpoint-recovery pass **without another Gmail call**: list completed searches, located/read documents, primary evidence, changed gaps, failed operation, outstanding P1 sources and one next micro-batch. Only then resume.

## Permanent operational principle

> **Exhaustive across the programme; micro-batched in each execution. Preserve the state before making the next connector call.**
