The 30-Aug-2026 revision deliberately distinguishes:

- **presentation caret** (`Name^` in existing repository/public prose): canonical

- **user-command caret** (`^` entered by Gil Marer): full registration,

## User-command scope

The command applies to any material object, including people, legal/commercial
entities, institutions, professionals, witnesses, proceedings, appeals,
incidents, piezas, filings, decisions, evidence items, source documents, ACTAs,
emails/communications, events, dates, transactions, financial flows,
properties/assets, contracts, allegations, theses and unresolved issues.

For each target, the mandatory question is not merely whether it is mentioned.
The audit asks whether it is:

1. registered in the appropriate federated register(s);
2. uniquely/canonically identified or keyed;
3. provenance- and evidence-status graded;
4. connected to the significant people/entities/proceedings/evidence/events/
   assets/issues that give it meaning;
5. bidirectionally discoverable where material;
6. placed in the correct proceeding/evidence and chronology context;
7. separately checked for repository, manifest, deployment and actual live state
   where publication is relevant;
8. gap/duplicate audited and safely repaired where authorised; and
9. reconstructable without the originating ChatGPT thread.

## Command statuses

Use: `VERIFIED`, `PARTIALLY VERIFIED`, `GAP FOUND`,
`UNRESOLVED / SOURCE REQUIRED`, and `REPAIRED`.

Never use a prior ChatGPT assurance as proof of repository or live status.

## Deletion-safety boundary

This continuity control is sufficient to preserve the intended meaning of the
`^` command in Git after merge because the canonical protocol and this handoff
state the distinction, scope, audit sequence and status contract independently
of the originating chat.

This does **not** authorise deletion of native evidence, private custody sources,
backups or other retention-controlled material, and it does not establish that
any particular target has passed a `^` audit until that target is actually
checked against its underlying registers/sources/live state.

## Future-thread recovery instruction

If a future thread contains only `^`, first recover the relevant continuity
context where available, identify the immediately relevant prior/referenced
matter, then run the canonical user-command protocol. Do not reduce the command
to identity-only verification and do not ask the user to repeat information that
repository/continuity sources can resolve.
