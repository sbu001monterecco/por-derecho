# CROSS-SYSTEM LIVE COORDINATION, CONTINUITY & MEMORY PROTOCOL

**Control ID:** `PD-GOV-XSYS-20260924-01`  
**Status:** mandatory coordination control  
**Scope:** GitHub, GitLab, Google Drive, connected-source records, ChatGPT threads/continuity, ChatGPT Memory orientation, public Pages/deployment and all multi-agent Por Derecho / Project Sun Rock work.

## 1. Why this exists

Por Derecho is now too large for "it was updated somewhere" to be an acceptable state description.

The same factual proposition can appear in:
- a native source;
- a preserved Drive copy;
- a GitHub/GitLab register;
- a public page;
- a ChatGPT conversation or handoff;
- an account-memory summary.

Those surfaces do not have the same evidential authority, update cadence or publication state.

The governing rule is:

> **No silent divergence. No silent promotion. No "all updated" without verified state.**

## 2. System roles and authority

### A. Native / originating source
Examples: court act, official receipt, native email, original attachment, bank/corporate/registry record.

This is the controlling evidential source for what that source establishes. A summary, mirror or AI memory never replaces it.

### B. Google Drive
Primary role: private/native evidence custody, controlled working records, human-readable control documents and preservation.

Drive custody proves only the state recorded by the specific source/custody controls. A Drive copy is not automatically the native original, public, filed, served, admitted or examined.

### C. GitHub
Current role: canonical public repository/integration and normal protected publication route unless a later express control changes that state.

Before every write:
1. read current `main`;
2. identify the one active integration lane;
3. compare the proposed delta against current `main`;
4. do not merge stale assumptions.

### D. GitLab
Current role: mirror, independent review/CI, alternative publication/verification surface and recovery/continuity layer.

GitLab may expose a different CI failure or preservation rule from GitHub. That difference must be recorded, not hidden and not automatically treated as evidence that the content itself is wrong.

### E. Connected Gmail / other source systems
For native emails/messages, the connected mailbox object is a source locator and may be the authoritative live source until separately exported/hashed. Repository summaries do not replace the mailbox record.

### F. ChatGPT conversation / handoff
Operational context, drafting history, user instructions and analytical continuity.

A chat is not primary evidence merely because it contains a factual statement. When the fact matters, return to the primary/native source or controlled repository record.

### G. ChatGPT Memory
Memory is an orientation and continuity aid only.

Memory must never be treated as:
- primary evidence;
- proof of current repository/deployment state;
- proof that a correction propagated;
- proof that an external action occurred; or
- authority to override a newer source.

Material memory-derived facts must be reconciled against current sources before consequential use.

## 3. Source/state precedence

For evidential content, prefer:

`native primary source → authenticated/preserved copy → official procedural record → controlled source register → reviewed analytical digest → public narrative → chat/handoff → memory`

This is a source-authority order, not a universal legal hierarchy.

For repository/deployment state, prefer:

`live provider state/current main → exact PR/MR/commit → deployment receipt/readback → handoff summary → memory`

## 4. Single live integration lane

GitHub issue **#1428 — Control Tower — Multi-thread integration queue** remains the live coordination node.

- Research and evidence acquisition may run in parallel.
- Only one integration/publication lane should normally own a logical release.
- Worker threads return structured deltas; they do not create competing canonical universes.
- If `main` advances materially while a branch is open, the integrator must refresh/rebase/rebuild from current main before claiming release readiness.
- A branch that fails a preservation gate because it predates a protected predecessor should normally be rebuilt from current main rather than weakening the gate.

## 5. Required worker/handoff envelope

Every consequential worker or thread handoff should state:

`objective / scope / canonical IDs / native sources / source status / corrections / new propositions / adverse evidence / open gaps / files changed / systems changed / current-main conflicts / external actions actually completed / actions not completed / PR-MR-Drive identifiers / readiness state`

Do not use "done", "synced", "fully updated", "live", "filed" or equivalent unless that exact state is verified.

## 6. Cross-system parity states

Every material cross-system object should be classifiable as one of:

- `EXACT_PARITY` — same intended bytes/content and same material status;
- `FUNCTIONAL_PARITY` — different provider implementation, same controlled proposition/function;
- `PENDING_PROPAGATION` — accepted change not yet written to another required surface;
- `INTENTIONAL_DIVERGENCE` — difference is deliberate and documented;
- `BLOCKED` — propagation attempted but blocked by provider/CI/permissions;
- `STALE` — surface is behind the current canonical source;
- `SUPERSEDED` — preserved historically but no longer current;
- `UNKNOWN` — state has not been verified.

Never infer parity from matching filenames or similar wording.

## 7. Correction propagation

When a material correction is accepted:
1. identify every dependent proposition, chronology, actor, entity, proceeding, public page and control;
2. propagate NEW→OLD and OLD→NEW consequences;
3. record supersession rather than silently rewriting history;
4. reconcile GitHub/GitLab/Drive where each surface is in scope;
5. update the active handoff/control state;
6. treat ChatGPT Memory as potentially stale until the user-facing Memory summary is separately updated.

A correction is not complete merely because the latest chat contains it.

## 8. Mutation receipts

Every consequential write should preserve the strongest available receipt:

- GitHub: repo + branch + commit SHA + PR + merge SHA;
- GitLab: project + branch + commit SHA + MR + merge SHA/pipeline state;
- Drive: file ID + URL + revision/modified-time where available;
- Gmail: message ID + thread ID + SENT/DRAFT state;
- public deployment: exact deployed SHA/build + route readback where tooling permits.

If readback is unavailable, say so.

## 9. Drive-specific controls

- Evidence custody and repository continuity are separate.
- Do not move, rename, overwrite or deduplicate native evidence without checking custody/provenance consequences.
- Prefer stable file IDs over filenames.
- Keep private/native material out of public Git unless explicitly cleared.
- A human-readable Drive control document may mirror governance, but repository rules remain separately version-controlled.
- Use the existing Por Derecho Evidence Manifest for custody status rather than inventing a competing evidence ledger.

## 10. Memory-specific controls

ChatGPT Memory should contain durable orientation only: canonical entity names, standing analytical rules, stable preferences and high-level project architecture.

Do not rely on Memory for:
- latest proceeding status;
- latest branch/PR/MR;
- whether a filing/email was sent;
- current balances/limits;
- current institutional office-holder where time-sensitive;
- exact evidential conclusions that have since been superseded.

If a durable Memory correction is material, flag it explicitly for the user. Full account-memory summary changes remain a separate user-controlled Personalization action; repository/Drive updates do not themselves prove the account Memory summary changed.

## 11. Live coordination loop

For any substantial multi-system task:

`READ CURRENT STATE → COMPARE → CLASSIFY DELTA → APPLY ONE CONTROLLED WRITE LANE → VERIFY RECEIPT → PROPAGATE REQUIRED MIRRORS → RECORD DIVERGENCE/GAPS → UPDATE CONTROL TOWER → HANDOFF`

Do not run concurrent writes to the same canonical files from separate agents.

## 12. Public/private boundary

Cross-system synchronization is not permission to publish private evidence.

Maintain:
- native/private custody;
- public-safe derivative;
- publication approval;
- deployment state

as separate states.

## 13. External-action boundary

Repository/Drive governance changes do not authorize:
- filing;
- service;
- email;
- regulator/prosecutor contact;
- journalist contact;
- social publication;
- payment;
- contract acceptance.

Those actions require their own authorization or an already-authorized workflow.

## 14. Self-audit

Before saying "GitHub, GitLab, Drive and ChatGPT are fully aligned", verify:
- current GitHub main;
- current GitLab main;
- relevant Drive file IDs/current content;
- active Control Tower/integration lane;
- known blocked/stale objects;
- latest correction dependencies.

If any required surface remains pending, say **PARTIAL — NOT FULLY ALIGNED** and name the exception.

## 15. Human-AI cooperation principle

The coordination system exists to preserve human agency and evidential integrity.

AI may coordinate, compare, draft, test and propagate controlled changes. It must not convert system synchronization into factual corroboration.

**One history can have many surfaces. It must not acquire many incompatible truths.**
