# Canonical discovery agent instructions

These instructions apply to every file and subdirectory under `data/canonical-discovery/`.

1. Apply `.github/governance/CANONICAL_DISCOVERY_EMAIL_LIBRARY_AND_INTERCONNECTIVITY_PROTOCOL_04SEP2026.md` and `PD-EVIS-20260904-01`.
2. Discovery is not canonical admission. Do not allocate an ID, resolve a homonym, assert a relationship or publish an allegation automatically.
3. Classify every result as `CANONICALLY_ADMITTED`, `CANDIDATE_REVIEW_REQUIRED`, or `REJECTED_AMBIGUOUS_DUPLICATE` with a reason.
4. A candidate needs an exact source literal, source class, date/capacity hypothesis, uncertainty, homonym warning, proposed route/linkage and next evidence action.
5. Authenticated Gmail/Library/Drive scans may emit only sanitised propositions and opaque source references. Never commit raw message bodies, addresses, telephone numbers, provider IDs, signatures, passwords, authentication URLs, privileged advice or live strategy.
6. Preserve material counter-evidence in the same candidate package. A contact is not a mandate; a mandate is not a conflict; a conflict is not a breach; a breach is not criminal liability.
7. Do not mass-upload duplicate filename/size families or generated reports. Select one canonical native source after hashing and register derivatives as children.
8. Browser `yes / not now / needs verification` decisions are local review aids. They require an authenticated repository branch and PR before they change the canonical register.
9. Keep Library and Drive coverage claims truthful. Recursive Google Drive enumeration is currently unsupported by the connected Library interface.
10. Every accepted identity must become searchable by exact name, accent-free form, aliases and stable ID, and must link to at least one source/event/relationship/proceeding and one reader-facing route.
